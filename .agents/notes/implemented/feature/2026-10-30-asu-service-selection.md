# Agent Note: 构建服务与固件目录选择

Status: implemented

## Problem

用户要求一个页面同时构建 OpenWrt 和 ImmortalWrt，先选择系统，再选择对应后端与配置。只修改请求地址会混用发行版元数据：ImmortalWrt 官方与 KyaruCloud 的 `/api/v1/overview` 返回 `upstream_url=https://downloads.immortalwrt.org`，其版本和修订号不能视为 OpenWrt 官方版本。

反复切换还会重复请求同一目录。2026-10-30 浏览器实际复现第二轮切回 OpenWrt 时，`https://downloads.openwrt.org/releases/25.12.6/.overview.json` 返回 HTTP 501、空响应体（`content-length: 0`，CDN `x-cache: MISS`），下一轮相同 URL 返回 200。地址和版本匹配；证据指向该次目录请求的临时失败，无法据此确定下载站内部故障原因。

同一目录内快速切换型号也需要隔离请求。浏览器延迟 A 的设备详情、先完成 B，再释放 A 时，输入框仍显示 B，但设备信息、默认软件包和分享链接都被 A 覆盖；目录代次相同，因此仅检查目录/版本不能防止此问题。

## Decision

由 `config.asu_services` 声明服务 id、distribution、名称、ASU 地址、固件元数据地址和根分区大小上限。界面由 distribution 派生系统选择，再筛选同系统的服务，避免重复维护两份配置树。预置 OpenWrt 官方、ImmortalWrt 官方和 ImmortalWrt/KyaruCloud，默认 OpenWrt；旧的单 asu_url 配置仍可运行，缺失 distribution 时使用顶层设置或 OpenWrt。

两级选择位于型号输入之前，自动读取对应 `.versions.json`、版本 `.overview.json` 和设备 `profiles.json`。服务可覆盖默认额外包、快照开关与设备信息链接；ImmortalWrt 默认不追加 OpenWrt 的全局额外包。系统/服务切换清除已选设备，重新选型时按对应数据源填充软件包；高级选项继续保留。脚本最初共用编辑内容，现由[按系统保存脚本草稿](2026-10-30-uci-defaults-drafts.md)接管：跨系统恢复各自草稿，同系统后端继续共用。构建信息显示系统与服务，页脚下载入口跟随固件目录。

分享链接仍以服务 id 为唯一恢复入口：已有 `asu=immortalwrt` 保持指向 KyaruCloud，新增 `asu=immortalwrt-official` 指向 ImmortalWrt 官方；由服务恢复其 distribution。切换系统时只在同系统候选中解析默认服务，不让全局 asu_url 或旧分享 id 越过分组。

根文件系统大小按服务校验：OpenWrt 官方 1024，ImmortalWrt 官方及 KyaruCloud 4096，留空省略字段。切回较小上限时保留输入并提示校验，不静默改写用户值。POST、轮询和结果下载绑定同一服务及设备快照；构建期间禁用系统/服务/型号/版本选择。新请求取代旧请求时丢弃旧异步结果。

`www/js/catalogue.js` 只处理版本列表与型号总览的 GET：按完整 URL 合并在途请求，成功 JSON 在当前页面缓存 5 分钟、最多 32 项；两个 ImmortalWrt 服务使用相同 URL 时复用，跨系统或版本分别存储。每次返回独立 JSON 副本，避免 `normalizeOverviewProfiles` 的原地修改污染后续选择。缓存到期后重新读取，刷新页面清空缓存。

网络错误或 HTTP 5xx 等待 500ms 后仅重试一次，重试用 `cache: reload` 重新读取响应。404、其他非 5xx 状态及 JSON 语法错误不自动重试；失败不缓存，最终 HTTP 错误显示 URL 与状态码。已有静态版本配置仍能在版本列表返回 HTTP 错误时回退。目录代次继续隔离旧响应，设备详情的迟到成功、错误也不能清除或覆盖当前提示；版本切换清除旧搜索处理器及候选列表。此策略不作用于构建 POST。

型号自动补全同时维护选择代次。每次编辑输入或选择候选都会作废此前的设备详情响应并清空待构建设备；详情只有同时满足当前目录与当前选择时才能写入。清空后重新输入相同名称也产生新代次，旧错误不能覆盖新型号提示。成功先设置当前设备，再更新显示、默认包与链接，使地址栏和构建请求使用同一设备；鼠标候选及 Enter 路径遵循同一规则。

`tests/test_services.py` 将关键跨模块契约固定为 Firefox 浏览器用例，沿用现有 pytest 与 simplehttpserver。测试读取实际页面、部署配置和本地模板，目录与 ASU 由路由提供固定响应，其他远端请求直接阻止并判失败。三服务提交/轮询/下载、容量校验、源与公钥、脚本草稿、目录失败重试和型号逆序响应均可独立重复验证；已有 CI 自动发现这些用例，README 提供本地安装及执行命令。

浏览器测试的 HTML 文档由路由直接读取仓库 `www/index.html`，其余本地资源仍由测试服务器提供。这样保留真实页面内容，并隔离本机 HTTP 扫描器注入的额外脚本；不对未知外部域名添加豁免。Python 虚拟环境需先激活，确保 simplehttpserver 通过 PATH 启动的是同一环境的 Python，测试后释放 8000 端口。

## Alternatives considered

- 只添加地址下拉框：改动最少，但会向 ImmortalWrt 服务提交 OpenWrt 元数据，故必须联动固件目录。
- 切换时刷新整个页面：易于隔离状态，但会丢失用户编辑的软件源、公钥和启动脚本；采用局部重载目录并隔离异步响应。
- 任意地址输入及运行时探测全部能力：配置更灵活，但引入跨域探测失败、动态 schema 差异及错误回退。当前采用可扩展的部署服务清单，限制由已核实配置声明。
- 保留混合的单个服务下拉框：状态更少，但不能满足用户先选系统再选后端的明确操作顺序；保留平面配置，仅将界面分为两级。
- 更换为 ImmortalWrt 仓库重新实施功能：更贴近单一发行版的部署默认，但会重复维护已有高级选项；两者使用相同的原生页面和 ASU 协议，因此在当前项目合并配置与选择流程。
- 仅重试每次目录请求：能处理首次临时失败，但仍在每次切换时重复下载同一总览；采用短时缓存并保留有限重试。仅取消旧请求也无法处理已经完成加载后的往返切换，因此继续用代次隔离，并允许同 URL 的新选择共享在途请求。
- 仅比较请求发起时的型号名称：改动更少，但切走再切回相同名称会重新接受旧响应；采用选择代次，并在编辑阶段清除构建设备，避免等待期间沿用上一型号。
- 只保留 Node 单测与临时浏览器验证：执行成本低，但无法长期检查页面事件、表单和服务配置的组合；复用原有 pytest/Firefox 工具链保留这些操作场景。真实 ASU 构建仍需另行验收，测试不依赖在线排队或创建远端任务。

## Consequences

用户能在两个发行版、三个服务之间选择，同时避免跨发行版混用元数据。代价是目录切换、分享参数和构建生命周期需要共同维护。构建期间禁用系统、服务与设备选择，服务清单的扩展需要编辑部署配置。自定义软件源和全局 device_packages.json 不会自动转换为另一发行版的软件包；用户与部署者负责选择兼容内容。

短时缓存减少重复切换的外部请求，但目录更新最多延后 5 分钟被重新加载感知，用户可刷新页面立即重新读取。独立副本和最多 32 项缓存增加少量内存与复制成本；有限重试在持续故障时增加一次请求和 500ms 等待。缓存及重试不能修复下载站自身，持续失败仍提示并禁用型号输入，不回退到另一发行版或静默使用过期数据。

保留 Firefox 回归增加浏览器安装、运行时间及空闲 8000 端口的要求；固定元数据样例需随服务 ID 和地址契约更新。它验证页面与请求的组合行为，在线目录可用性、真实构建及设备刷机仍需单独验收。

预置服务的可用性和上限可能改变，维护者须重新核对服务接口。KyaruCloud 的单设备 JSON 接口在本次读取时返回过 500，不能以元数据可读或模拟测试替代真实构建验收。第三方服务接收所选软件包、公钥及首次启动脚本，页面展示实际地址和对应发行版。目录加载来自固件下载站，不依赖本次返回 500 的 ASU 单设备 JSON 接口。

2026-10-30 核实 ImmortalWrt 选择器仓库 `30c511175ba8f9cbdbd21bf1bb565c98bc25a01b` 默认 KyaruCloud，线上 config.js 却默认 `sysupgrade.immortalwrt.org`，因此源码默认和实际部署须分别核查。ImmortalWrt 官方当前 `repository_allow_list` 仅列 `https://nikkinikki.pages.dev`；页面说明自定义源受所选服务策略限制，不因 API 存在 repositories 字段就承诺接受任意源。
