# Agent Note: 版本内容与动态证据组合生成双语发布说明

Status: implemented

## Problem

首发工作流只从中文提交生成简短说明，用户满意的完整双语正文由 Agent 在发布后另行补充，后续版本无法复用。第一次完善还只检查了 Markdown 格式与本地文件，遗漏 GitHub Release 不自动生成标题锚点、原始 id 会加 user-content 前缀的差异。仅把首发正文写死到脚本会复制过时测试数字、首发基线与交付状态。

## Decision

每个版本使用 docs/releases/标签.zh-CN.md 与 docs/releases/标签.en.md 两份 Markdown，维护简介、亮点、环境、使用部署、限制和鸣谢。模板提供固定的五个二级章节；缺语言、缺章节或 TODO/TBD 未替换即失败。人工内容与本版本代码一起评审，不从提交标题猜测支持环境、实机覆盖或已知限制。

scripts/release_notes.py 继续持有标签、上游排除、提交范围和发布产物契约，组合双语正文、完整提交链接、基线对比、生成时间和资产表。scripts/release_content.py 负责版本内容读取、相对链接固定及渲染链接验证。使用 Python 标准库和工作流已有 gh，不引入模板引擎、Markdown 依赖或翻译服务。

每种语言在个人提交分类后独立展示“完整更新日志 / Full changelog”，标明前一版本到当前版本并链接至 GitHub compare。该入口复用已解析的基线 SHA 与当前标签，覆盖区间内的全部提交和文件变更，包括合入的上游更新；没有前版标签时沿用初始基线回退。个人提交分类继续保持上游排除规则，当前版本说明修订时同步 Release 正文与说明下载资产。

现有发布工作流直接调用该生成器，使用生成文件作为正文并上传同一文件，因此无需再加一层工作流拼接。命令行回归在带上游合并的临时 Git 仓库中验证无目标标签预览和正式生成，解析两种语言的比较范围并检查范围内含上游提交；首版基线和普通前版选择由现有回归覆盖。

CLI 夹具显式传入 `--repository example/selector`，同时模拟另一个 `GITHUB_REPOSITORY` 环境值，验证参数优先级并隔离实际 CI 仓库。否则只在没有该环境变量的本机通过，GitHub Actions 中会把比较链接生成到运行所在仓库，导致夹具范围断言失败；生产 CLI 读取 CI 仓库的默认行为保持原样。

正式生成读取标签内的两种语言，要求 HEAD 同标签，已合入 develop 且不是纯上游；预览明确使用 HEAD 与工作区内容，不创建 Git 标签。Git blob 的 CRLF 在读取边界统一成 LF，与工作区文本读取保持一致，避免 Windows 文件误判为缺少章节。两种模式均核对实际 ZIP、同名校验文件及包内外 build-info；正式模式额外拒绝脏站点。预览中的未来标签/下载链接不代表已发布。

发布正文使用显式带 id 的语言标题，并将跳转目标写为 GitHub 清洗后的 user-content 名称。相对文件链接转成当前标签的完整 GitHub 地址；本地检查文件、提交、版本对比及计划上传的资产名。正式工作流调用 GitHub Markdown API，核对实际渲染的 href/id，拒绝丢失链接和无目标片段。外站只做 HTTPS 格式检查，不因第三方临时不可用阻断发布；这延续网站 HTML 检查的外链可用性边界。

生成时间明确标为说明生成时间，不冒充实际发布时间；工作流链接代替固定测试计数，不在创建 Release 前声称发布或通知已成功。相同完整正文保存为 build/release-notes.md，并同时作为 Release body 和下载资产；发布任务继续拒绝覆盖已有 Release。

## Alternatives considered

- 发布后由 Agent 补全文案：最灵活，适合首发修正；但每次发布都有时间窗口显示简版，文案不在标签中，无法保证接力后的可复现性。
- 脚本写死完整首发正文：单次运行方便；但环境、限制、测试数字和首发描述会误用于后续版本，不能替代逐版本审定。
- 让提交标题或在线模型生成全部内容：省去版本文档；但提交不足以证明支持环境与验收范围，也会引入翻译服务、凭证和网络依赖。只自动化可从 Git 与产物推导的事实。
- 发布时检查所有外链 HTTP 状态：能发现目标服务下线；但新资产尚未上传，第三方限流/故障不代表说明链接错误。自有路径和实际渲染是硬门禁，外部服务联网验收单独进行。
- 仅保留基线表格中的比较链接：无需新增正文，但入口含义不明显，用户容易把个人提交列表当成全部变更；独立小节展示完整比较，不再复制另一份全量提交清单。

## Verification

工具回归覆盖双语组成、前一标签与上游排除、缺语言/章节/占位内容、标签与工作区隔离、无标签预览、包摘要/元数据与脏站点、失效锚点及 GitHub 渲染失败。真实渲染只调用 Markdown API，不创建 Release 或发送 Telegram；本地预览产物在使用完成后清理。

44 项工具测试通过，其中版本说明测试显式写入 CRLF，避免仅在 Windows 才能发现换行差异。实际 79 文件站点包生成完整双语预览，并通过 GitHub Markdown API 校验；5 份工作流通过 actionlint 1.7.12，3 个变更实现/工作流文件的 Semgrep 扫描无发现或执行错误。6 份说明/模板的 34 个相对文件链接与 12 篇笔记三项门禁通过。

完整更新日志自动化通过全部 45 项工具回归，包含命令行预览、正式生成、首版与前版范围检查。使用 site-v1.0.1 的三项正式构建资产实跑 CLI 并校验 GitHub 渲染，输出除生成时间外与已审定公开说明一致；该验证的四个临时文件和目录已自动清除。site-v1.0.1 的中英文入口实际点击均显示前版至本版的 4 个提交、19 个文件，含上游翻译；公开正文与说明下载资产回读一致，其余三项构建资产保持原值。

## Consequences

新标签一次生成完整正文，版本内容、动态数据与下载文件保持一致；代价是每次发版前维护两份内容，并在正式发布时依赖 GitHub Markdown API。模板缺失会及早阻断，维护者应先运行预览命令。故意保留中文提交原文，用户说明提供双语；不自动翻译提交或宣称外部服务可用。

自动化已在 site-v1.0.1 正式流程中运行；新增完整更新日志的生成器改动需随后续代码交付才用于下一版，不能把当前 Release 文案修订当作生成器已经推送。
